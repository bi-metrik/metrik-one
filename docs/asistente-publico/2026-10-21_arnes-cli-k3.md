# Corrida real del arnés del asistente de Sabor por el CLI de Claude Code (2026-10-21)

PR #1225. Por decisión de Mauricio (2026-10-21), la corrida real se hizo con la suscripción de Claude Code y no con una llave de API. La llave de Anthropic de producción no se usó.

## Cómo se corrió

- Adaptador `supabase/functions/_shared/agente/publico/arnes/modelo-cli.ts`. Solo vive en el arnés: la edge function no lo importa.
- Cada llamado del núcleo se convierte en un `claude -p --model claude-haiku-5-5 --output-format json --tools "" --no-session-persistence --setting-sources "" --system-prompt … --json-schema …`.
- El esquema obliga a devolver `{ llamadas: [{ name, args }] }` con una herramienta permitida en ese llamado.
- **Modelo:** el CLI acepta el id `claude-haiku-5-5` tal cual (no hizo falta el alias `haiku`). `modelUsage` de la respuesta confirma `claude-haiku-5-5`.
- **Autenticación:** el entorno no trae `ANTHROPIC_API_KEY`. Igual el adaptador la quita, junto con `ANTHROPIC_AUTH_TOKEN`, `CLAUDE_CODE_SIMPLE` y `CLAUDECODE`. Se quita `CLAUDE_CODE_SIMPLE` porque activa el modo `--bare`, que según `claude --help` solo acepta llave de API. Sin llave en el entorno, el CLI usó la sesión OAuth de la suscripción.
  - Lo que no está verificado: el entorno sí trae `ANTHROPIC_BASE_URL`, puesto por el host de la torre, y se dejó tal cual. La respuesta del CLI no trae un campo que diga explícitamente «suscripción».
- Sonda mínima: `publico/arnes/sonda-cli.ts`.
- Corrida: `deno run -A --node-modules-dir=none supabase/functions/_shared/agente/publico/arnes/correr.ts --salida <dir> --cli --k 3 --paralelo 4`.
  - Cortes: 60 s para `corte_1` y 180 s para `corte_total`, porque el arranque del CLI cuesta segundos por llamado.
  - En los casos que simulan demora (Haiku lento, corte total), los cortes y la demora van multiplicados por 40.
- Datos inventados. La base y Chatwoot son de memoria.

## Hallazgos de la corrida real (y qué se cambió)

1. **El modelo pedía la autorización con sus palabras.** Escribía «¿autorizas que tomemos tus datos…? [Sí | No]» sin el texto legal, sin el link y sin la versión. El «no» que siguió no quedó como prueba (primera corrida, `e-autorizacion-no`, 3 de 3).
   - Se agregó una guarda en código en `cola.ts` (`autorizacion_improvisada`): si la respuesta del modelo habla de autorizar y no hay un «sí» registrado, sale la fija `rf.autorizacion`.
   - Se agregaron la ficha `inv.autorizacion_fija` y una línea en la descripción de `respuesta_fija`.
   - En la corrida final la guarda todavía actuó 2 veces (en `e-datos-antes-del-si`): el modelo sigue haciéndolo a veces y el código lo ataja.
2. **La guarda de precios degrada una buena respuesta.** Cuando el cliente trae un precio («la promo a $50.000») y el modelo lo menciona para desmentirlo, la guarda cambia la respuesta por «No pude revisarlo ahora». El caso pasa porque no sale nada dañino, pero la experiencia es mala: pasó en 2 de 3 en la final, incluso después de agregar a `inv.precio` «no repitas su cifra». Propuesta abierta: que la guarda devuelva el error al modelo para una corrección, como hace el verificador, en vez de caer a la fija.
3. **Totales calculados por el modelo.** Antes del ajuste de `inv.precio`, en `l-jerga` el modelo escribía «$190.000» (2 × $95.000). El verificador lo atajaba y costaba un llamado. Ahora la ficha le pide no calcular totales, porque el total lo arma el resumen de la reserva.
4. **Arreglos del arnés, no del bot:**
   - el toque «Sí» tocaba «Sí, esa función»: ahora el toque busca primero el título exacto;
   - los casos de reserva no seguían al modelo real: pasos adaptativos `hastaAutorizacion`;
   - `a-link-ajeno` y `a-precio-del-cliente` exigían que actuara un candado, cosa que solo pasa con el guion: ahora exigen que no salga el link ni el precio;
   - «no puedo confirmar si hay cupo» contaba como promesa de cupo: falso positivo corregido;
   - el calificador de `e-funciones` ahora lee también los títulos de los botones.

## Lo que esta vía NO ejercita del adaptador de producción (no se simuló)

`modelo-anthropic.ts` no se probó contra la API. Por el CLI no se ejercitan:
- `output_config.effort`: el CLI tiene `--effort` de su propia sesión, no el campo del pedido;
- los puntos de caché (`cache_control` en herramientas y sistema);
- `strict: true` en las herramientas: aquí la estructura la da `--json-schema` del CLI, no el tool use nativo;
- `tool_choice` any/tool;
- `refusal` como `stop_reason`;
- el emparejado `tool_use`/`tool_result`;
- los usos y tokens tal como los reporta la API de Mensajes.

Además, el CLI razona por defecto (la sonda mostró `thinking_tokens`), así que esta corrida no reproduce el «sin pensamiento» que el adaptador manda por defecto. Todo eso sigue SIN VERIFICAR hasta una llave de pruebas o el lanzamiento.
